1. CNS System Architecture

MailTrust is an academic Cryptography and Network Security (CNS) email authenticity engine designed to eliminate the ambiguity and unverifiability of black-box ML models. By leveraging deterministic cryptographic primitives and internet protocol specifications (RFC 6376, RFC 7208, RFC 7489), MailTrust evaluates whether incoming messages maintain cryptographic integrity, adhere to published domain sender authorizations, or exhibit structural spoofing techniques.

// CNS Verification Pipeline
1. Input Parsing → Safe MIME structure extraction (RFC 5322 & RFC 2047)
2. Cryptographic DKIM → Asymmetric RSA/Ed25519 signature & SHA-256 body hash verification
3. Network SPF → Envelope IP authorization checks & mechanism recursion (RFC 7208)
4. Policy DMARC → Organizational domain alignment against RFC 5322 From (RFC 7489)
5. Domain Heuristics → Confusables, Punycode (IDN), & display-name spoofing audit
6. Risk Engine → Transparent, explainable synthesis yielding one of 4 strict verdicts

2. Public-Key Cryptography in DKIM (RFC 6376)

DomainKeys Identified Mail (DKIM) provides non-repudiation and transit integrity via asymmetric public-key cryptography.

Body Hash Generation ($bh$)

The message body is canonicalized (simple or relaxed) and hashed using SHA-256. The resulting digest is stored in the bh= tag. Any post-signing alteration of a single byte invalidates this hash.

Header Signature ($b$)

The specified header fields (h=), including the bh= tag, are canonicalized and signed using the domain owner's private key ($K_{\text{private}}$). The signature is stored in b=.

Public Key DNS Resolution: Verifiers query the TXT record at:
<selector>._domainkey.<signing-domain>
Record format: v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQE...
CNS Distinction: Cryptographic Authenticity vs. Trustworthiness

A valid DKIM signature proves only that the owner of the private key for domain d= authorized this message. An adversary can register evil-domain.com, sign malicious emails with a valid 2048-bit key, and achieve DKIM PASS. Hence, DKIM alone does not establish safety without DMARC alignment.

3. RFC 7208 SPF Evaluation & Transient Limits

Sender Policy Framework (SPF) allows a domain owner to publish a list of IP addresses authorized to send mail on behalf of their envelope sender (MAIL FROM).

Supported SPF Mechanisms & Qualifiers:
  • ip4 / ip6: Direct CIDR subnet matching without DNS lookups.
  • a / mx: Authorizes host IPs or mail exchangers (triggers DNS queries).
  • include: Evaluates another domain's SPF record recursively.
  • all: Default catch-all mechanism.
  • Qualifiers: + (Pass), - (Fail), ~ (SoftFail), ? (Neutral).
RFC 7208 Limit Enforcement: Verifiers must terminate evaluation with PERMERROR if more than 10 DNS queries are required (counting a, mx, include, exists, redirect). MailTrust strictly enforces this limit and detects circular include loops.
Static .EML Limitation:

The connecting IP and envelope sender are transient SMTP protocol negotiations. In an offline .eml file, Received: headers can be spoofed by an attacker. MailTrust therefore labels SPF as NOT EVALUABLE unless the user provides verified SMTP connection parameters.

4. RFC 7489 DMARC Alignment & Domain Policy

DMARC binds technical envelope authentication (SPF and DKIM) to the end-user visible header (RFC 5322 From:).

DKIM Alignment (adkim)

Relaxed (r): The DKIM d= domain and From domain must share the same organizational domain (e.g. mail.example.com aligns with example.com).
Strict (s): An exact FQDN match is required.

SPF Alignment (aspf)

Relaxed (r): Envelope sender domain and From domain share organizational domain.
Strict (s): Exact FQDN match required.

// DMARC Decision Rule:
DMARC_PASS = (DKIM_PASS && DKIM_ALIGNED) || (SPF_PASS && SPF_ALIGNED)

5. Homoglyphs, Typosquatting & Display-Name Spoofing

Adversaries exploit human visual perception to impersonate trusted institutions without triggering standard technical authentication alerts:

Mixed-Script Homoglyphs

Substituting Latin characters with visually identical Cyrillic or Greek glyphs (e.g., Cyrillic 'а' U+0430 for Latin 'a' U+0061).

Punycode Encoding (IDN)

Internationalized Domain Names formatted with xn-- prefix to encode non-ASCII lookalikes in DNS.

Display-Name Spoofing

Setting friendly display names to mimic brands (e.g. "PayPal Alert" <attacker@evil.com>).

7. Known Limitations & False-Positive Scenarios

  • Legitimate Mailing Lists (Forwarding Breakage): Mailing lists often modify subject lines or footers, breaking DKIM body hashes. Without SRS (Sender Rewriting Scheme) or ARC (Authenticated Received Chain), legitimate list forwards can fail SPF and DKIM.
  • Shared Relay IP Ranges (ESP): Multi-tenant Email Service Providers (SendGrid, Mailgun) use shared IP pools. SPF passing confirms the ESP was used, but not necessarily that the tenant was benevolent.
  • DNS Latency & Timeouts: High-latency networks or recursive resolver throttling can produce TEMPERROR states, which MailTrust honestly reports without guessing.
  • Compromised Authentic Accounts: If an attacker steals genuine credentials and sends mail through the legitimate server, SPF, DKIM, and DMARC will all pass! Only content heuristics and behavioral context can detect this scenario.
